> Anthropic 副首席信息安全官 Jason Clinton 详述安全工程团队如何保护一个 AI 编写了 80% 合并代码的 SDLC。

在 Anthropic，代码量和部署速度呈指数级增长。我们的软件工程师每季度交付的代码量比 2021 至 2025 年间平均高出 8 倍。我们的审查、监控和其他安全流程必须跟上这一加速步伐，否则就会成为瓶颈（阿姆达尔定律）。

我们的软件开发流程也发生了根本性变化。Claude 已从编码助手演变为主要创建者和审查者。Claude 编写了如今合并到我们代码库中约 80% 的代码。超过一半的代码由我们内部的 Claude Tag 版本合并，而人类工程师专注于指导、设定意图和最终审批。

这意味着我们的安全团队必须防守一个快速扩张的攻击面，并在其核心有非确定性、不断演化的 Agent 的环境中加固生命周期。在本文中，我将介绍保护 SDLC 的策略。

（本文应与我们近期发布的 Zero Trust for Agents 框架结合阅读；本文中的所有内容在该框架中都使用了安全设计理念）。

我们所针对的威胁具体包括：被攻陷或提示注入的 Agent 引入恶意变更；Agent 作为可信输入摄入的供应链和依赖项投毒；以及更为熟悉的、以更高数量级出现的那几类应用漏洞。下文讨论的每项控制措施都至少对应其中一种威胁。

我们部署了若干总体策略来实现这一目标，同时不大幅限制开发速度，包括：将安全左移并完全集成到代码开发阶段；使用硬访问和身份边界来限制爆炸半径；在生产前和生产后结合自动化确定性审查和 Agent 审查；在最关键的节点让人类参与循环。

在本文中，我们将介绍在 SDLC 各阶段实施的安全流程及其背后的核心原则。随着模型能力的不断演进，安全团队必须重新审视并经常重新设计其流程，而这些原则更具持久性。

## 不断演化的软件开发生命周期 / The evolving software development lifecycle

我们的开发团队已在多个场合介绍过其软件开发流程的变革，因此这里只做简要概述，然后深入各阶段。

概括来说，我们的 SDLC 被大大压缩了。它更多由原型和内部采用（dogfooding）驱动，而非漫长的规划周期。创意来自组织的各个角落，传统角色（前端、后端、设计）之间的界限变得模糊。审查和审批仍然有人类参与，但也由 Agent 循环驱动。

虽然每个阶段都因 Claude Code 和 Claude Tag 而发生根本性变革和加速，但各阶段的名称和用途对来自更传统组织的开发者来说并不会显得陌生。这些是天然的关卡，我们也将其作为 AI 原生 SDLC 安全流程的一部分。

## 规划阶段 / Plan

我们最早的安全自动化之一是一个简单的由 Claude Opus 驱动的 PSR（项目安全审查）Web 应用。它读取项目设计文档，并对照 MITRE ATT&CK 框架分析潜在漏洞，提出缓解建议。我们通过将其连接到一个内部知识索引来显著增强该系统，该索引提供了涵盖组织范围策略、过往决策和相关系统的更深入上下文。

这让我们能更好地理解潜在风险，也能捕获 PSR 中缺失的信息。这一实现节省了 AppSec 团队的大部分时间。当我们对 Claude 评估风险的准确性有了信心后，我们允许团队在 Claude 认定发布风险足够低的情况下自行批准项目。

这里可以看到 AI 原生 SDLC 的首批关键适应之一。PSR 最初设计用于在漫长且昂贵的编码过程之前捕获安全问题——在这个阶段发现问题可以节省数月的重新开发时间。

如今，主要功能的多重原型可以在数小时内创建，这使得详细的架构审查不再那么关键。将我们的 PSR 应用连接到知识索引可以捕获原本可能被遗漏的上下文，而不会制造不必要的减速。为 Claude 创建 Claude Code skill 让 Claude 能够进一步扩展并在任何存在上下文的地方捕获它。

> **持久原则：将安全 Agent 连接到组织上下文。** 随着规划周期压缩，将这些 Agent 带到上下文已经存在的地方——聊天线程、过往审查、代码库——远比在可能不再需要的阶段强制要求详细文档更有效。无论如何，Agent 需要代码本身之外的上下文。

## 编码阶段 / Code

AI 原生工程组织中的安全专业人员有了一个新杠杆：他们可以直接影响代码的创建方式，在源头帮助预防漏洞。

过去，团队观察到反复出现的漏洞并创建安全编码指南来解决它们，但这些指南难以执行且很少标准化。在 Anthropic，这些指南被编码在 CLAUDE.md 文件和组织级 skill 引用中，使得代码在生成的那一刻就遵循这些最佳实践。这是作为一个闭环完成的——一旦 Agent 发现了一个 bug 类别，相关文件就会被更新以防止它在未来代码中再次出现。

当然，这并不意味着所有代码都完美无缺。我们的团队从一份指示 Agent 在打开 PR 前运行 `/security-review` 的 CLAUDE.md 文件开始。这个普遍可用的命令是我们团队内部审查流程的产品化版本，它会查找潜在的攻击者可控输入入口、扫描可疑链接，然后验证其发现。

如今，这些审查在 Claude 生成代码的过程中就已进行。一旦安装了安全指导插件，Claude 就会在对话和代码生成过程中实时审查，建议安全改进并处理常见漏洞。

在 PR 时刻的其他提示会推动内部非技术团队将其应用托管在我们的低代码应用托管平台上，从而避免了传统上困扰安全团队的影子 IT。

一些客户选择将 `/security-review` 与 PreToolUse hook 集成，使这一步成为更严格的关卡。这也同样有效，但我们的团队选择将硬性的代码审查关卡放在测试/CI 阶段。

除了塑造和审查代码外，限制爆炸半径是我们在这一阶段的主要关注之一。我们通过对身份设置硬边界（更多内容在监控部分）以及让开发者在虚拟机上编码来实现这一点。将编码迁移到远程 VM 是一个相对无痛的转变，与仅使用笔记本相比，它给了我们更强的控制和可见性。这些 VM 上的 Agent 流量被设置出站白名单。

这些严格的出站控制特别重要，因为 Agent 正在读取可能携带提示注入载荷的不可信输入。注入的指令无法到达互联网上的任意目的地：外泄路径被限制在一小部分受监控的服务上。

这里再次可以看到为 AI 原生 SDLC 所做的清晰适应。远程编码以前主要用于保护 IP，而现在越来越多成熟的 AI 编码团队采用这些环境来限制 Agent。

> **持久原则：在 AI 原生工程组织中，左移意味着在漏洞发现和更新指令以定制 Claude 代码生成方式之间形成闭环。通过硬边界限制爆炸半径（最小权限原则）和 Agent 可以访问的内容。**

## 测试（CI）阶段 / Test (CI)

根据我的经验，测试或 CI 阶段会很快成为 AI 原生转型过程中工程团队最痛苦的瓶颈。在 Anthropic，一旦大多数开发者开始使用 Agent 编码工具并同时运行多个 Agent，很快就发现团队的速度只能和人类审查代码的速度一样快。

需要明确的是：人类的问责制仍然是我们流程的核心。我们所做的是通过结合自动化 Agent 审查和确定性审查来加速审查过程，同时将人工审查保留给受监管或真正关键的代码。

历史上，人工代码审查一直被视为标准，但经验证据表明它并不完美。安全 bug 仍然会定期在全球的软件中上线。我们的审查流程能够审查更多代码并捕获特别复杂的问题，有助于降低这些风险。

获得实质性审查评论的 PR 比例从 16% 增长到了 54%，这是因为我们要求 Agent 为其发现编写证明，从而对其发现建立了信心。我们还确定，过去约三分之一的 claude.ai 事件背后的 bug 本可以被我们现在已实施的自动化流程捕获。

我们并非唯一发现这一点的组织。Intercom 分享了其自动化批准 19% PR 的经验——部署量翻倍，同时由破坏性代码变更导致的停机时间下降了 35%。CircleCI 在构建 Chunk（一个基于 Claude 的自主 Agent，可解决 CI/CD 维护问题并在人类看到之前自行验证修复）时也得出了类似结论——该方法将 Agent 任务转化为已完成 PR 的比率翻了一番。

当 PR 在 Anthropic 被打开时，多个 Agent 会自动审查它。每个审查 Agent 都针对特定的、狭窄的关注领域设计，并利用 RAG 获取围绕过去事件的额外上下文和记忆。这比单个巨型提示或超级安全 Agent 有效得多，原因如下：

- 它们不会共享偏见和盲点
- 如果一个被攻陷或出错，可以被其他审查者发现
- 精力不会过于分散在多个关注领域

需要说明的是，Agent 并非不加检查地合并代码到生产环境。我们按风险对代码库进行分级，并有意识地决定哪些部分可以自动化。整个代码库有严格的人工审批流程。

对于由 Claude 审查和合并的代码，人类问责制仍然至关重要。每次审批都记录了其信号和推理过程，并且会按风险加权抽样由人类审查。另一轮测试聚焦于不变量，如"用户 A 永远不能读取用户 B 的数据"，并触发额外的手动审查。我们还将 Agent 扫描与 SAST 工具结合使用，这些工具会直接发布在 PR 上。

大多数扫描方法，无论是 Agent 式的还是确定性的，都是基于消耗量的。成本会随着代码吞吐量的增加而增加，团队需要决定适合他们的覆盖水平。在 Anthropic，我们接受这里的成本会随着代码速度的增加而增长，但预计单位成本会下降。今天的模型在编码方面比几年前的任何模型都好得多，我们预计这一趋势将持续。

> **持久原则：自动化审查是一种不同类型的风险，需要不同的控制方式（通过多个关卡和具有独立上下文窗口的 Agent）。人类仍在循环中，但根据代码库的性质，他们可能位于生命周期的不同位置。**

## 部署（CD）阶段 / Deploy (CD)

Anthropic 维护一个健壮的预发布环境，在其中执行常见的安全最佳实践，如主要发布的外部渗透测试和定期 DAST 扫描，以捕获静态扫描遗漏或无法看到的逻辑 bug。

与其他 SDLC 阶段一样，AI 为安全团队同时带来了新挑战和新解决方案。一方面，更少的漏洞到达这个阶段。另一方面，确实存活的漏洞是最微妙、最难捕获的。再加上更大量的代码以更高频率发布，定期的动态测试似乎不再那么动态了。

好消息是 AI 模型在多步骤、跨组件的推理方面表现更好，可以捕获更大比例的这些复杂漏洞。例如，2 月份我们披露 Claude 发现并帮助修复了超过 500 个高严重性 OSS 漏洞。

在 Anthropic，我们正在预发布环境中实施持续的 AI 驱动 DAST 扫描。这些扫描在系统级别寻找漏洞——即两个或多个服务之间的假设不正确的地方。目前已有多个供应商提供这些能力。

> **持久原则：动态测试应与部署节奏相匹配。**

## 监控阶段 / Monitor

任何一个好的安全团队都知道，代码推送到生产环境后工作并没有结束。我们可以假设任何漏洞都会被日益复杂的攻击者迅速发现。

我们的安全团队实施了标准的实践，如公开的漏洞赏金计划、红队模拟攻击，以及跨依赖项、密钥、供应链、云配置和容器的定期漏洞扫描。Claude 在这些工作中扮演重要角色，但我们将重点关注因 AI 原生 SDLC 而带来的监控方面的更大变化：告警分类和代码迁移。

当 Anthropic 有告警触发时，Claude 会开始：读取生产日志、定位 bug 根因、编写事后分析报告，以及在某些情况下编写修复 bug 的代码变更。但这个 Agent 不能做的是自动部署修复。它是一个单一用途的系统账户 Agent，只有三个权限：写入新文档、在公司频道发帖、访问生产日志。

修复需要来自一个独立的 Agent-人类审查系统。原因又回到了管理身份、权限和硬边界：在将代码推送到生产环境时限制爆炸半径至关重要。分离 Agent 是关键，因为一个（或多个）Agent 充当了另一个 Agent 的制衡。

这也是对 CISO 的重要教训，我是通过艰难的方式学到的。在考虑 Agent 的硬边界时，你需要包括它访问其他 Agent 的能力。在一次模型升级后，事件响应 Agent 主动通过 Slack 联系了另一个 Claude 实例——它请求那个可以编写代码的 Agent 推送修复。这被设计的人工审查关卡捕获了，但这次经历教会我们划定边界要围绕访问和行动，而不是围绕模型的指令或我们认为模型能做什么。如今在 Anthropic，Agent 之间的 Slack 通信已是常态，我们对 Agent 身份模型给予了大量思考。

第二个重大变化是我们的团队处理迁移的方式。每个安全工程团队都经历过这样的时刻：他们意识到需要进行代码迁移来修复公司运营方式中的某些系统性缺陷。过去，CISO 需要开始游说，并申请每个部门工程资源的一小部分，持续多个季度才能修复。现在，迁移的经济成本已经下降，跨公司协调的成本也下降了。Claude 在数天内自动完成迁移过程——数万行代码的迁移。

> **持久原则：给每个 Agent 一个单一用途的身份，配备完成其工作所需的最小权限。如果确实让 Agent 协调，让它们在人类使用的同一渠道上进行。**

## 治理 / Governance

我们已经自动化了许多安全流程，但人类仍然是我们确保安全软件开发生命周期的不可或缺部分。不过，我们的注意力不再集中在审查代码和 bug 报告上，而是集中在 Claude Tag、循环和仪表板上。

这凸显了强治理的重要性。如果一个 skill 过时了、发现的 bug 类别从未回到 CLAUDE.md 中、或者 Agent 的决策没有经过抽样审查，整个结构就会退化。我们通过以下方式避免这种情况：

- 按风险对代码库分级，然后基于该级别自动化审查。
- 对所有新 AI 审查者使用影子模式。新 Agent 发布评论供人类批准，直到赢得信任。我们的团队还会对其进行"红队"测试，尝试插入恶意变更。
- 对所有自动化审批进行抽样。
- 监控我们的关键指标。我们维护并密切监控一个仪表板，汇总所有安全流程和工作流的关键指标。
- 将每个 Agent 操作路由到 SIEM。每次自动化审批、工具调用和 Agent 间消息都会记录其使用的信号并进入我们的 SIEM，因此任何决策事后都可追溯和审计。我们使用这些数据，将这些 Agent 视为一种新型内部威胁，并在它们行为异常时触发告警。

> **持久原则：安全工程师的工作从监控 bug 演变为监控循环。**

## 唯一不变的是变化 / The only constant is change

无论怎样强调都不为过——软件开发生命周期以及加固它的手段正在以极快的速度演变。模型能力每个月都在进步，带来新的挑战和解决方案。

今天不太奏效或在经济上不太可行的东西，很可能很快就会变得可行。你的团队应该问的问题不是"我们负担得起扫描所有东西吗"，而是"如果扫描几乎免费，我们会运行什么？"。为此做好准备。
